# Codex instructions — SieEncode Studio

These instructions apply to the entire `schaffrath94/SieEncode` repository. Read `README.md`, `docs/ROADMAP.md`, and the relevant feature/contract documents before making changes. This repository is the **Studio/project builder**, not the card execution engine.

## Scope and working method

- Preserve and improve the existing implementation; search for the current owner of a feature before introducing new classes, abstractions, workflows, or parallel implementations.
- Work on the requested backlog item only. Identify existing behavior, dependencies, acceptance criteria, and regression risks first. Avoid unrelated refactors and sweeping rewrites.
- Treat **RC15 as a preserved baseline**, not permission to replace or silently migrate project data. `rc15-source-baseline` and the original delivered binaries are provenance records, not fresh approvals.
- Prefer small, reviewable changes. Keep older project/profile/vault formats readable; never silently rewrite existing project definitions, profiles, version history, rfPrj files, payloads, or reports.
- Keep product behavior, UI, and documentation consistent. State any unresolved limitations clearly; do not declare a feature complete based only on a successful compile.
- When documentation disagrees, check current code and tests; `README.md`, `VERSION`, current build scripts, and explicit baseline records take precedence over historical version statements.

## Repository boundaries

- `SieEncode`: project/profile editing, versioning, vault access, project building, preflight, coding station orchestration, reports, and UI.
- `SieEncode.Runtime`: separately maintained RFiDGear-derived execution engine. It is normally cloned next to this repository; `runtime.lock.json` pins the RC15 source baseline. Do not casually update its pin or imply a new engine build is previously hardware-approved.
- `schaffrath94/RFiDGear`: upstream-oriented fork, kept separate for upstream contributions. Evaluate changes selectively; never blindly merge its history into the Studio or sanitized Runtime.
- RFiDGear owns reader/card polling, physical tasks, and card commands. Studio owns orchestration and evidence evaluation; do not duplicate the reader/crypto execution engine in Studio.
- Review the existing `RUNTIME.md`, `docs/RFIDGEAR-HOST-CONTRACT-V1.md`, `PARITY.md`, `MIGRATION.md`, and `docs/HARDWARE-ABNAHME.md` before changing their respective contracts.

## Security and correctness are non-negotiable

- Fail closed on unknown reader/runtime capabilities, mismatched binary versions or hashes, missing/uncorrelated task results, failed preflight, or ambiguous card state. A version label alone does not prove a capability.
- Never report a card operation as successful without the required authoritative terminal status, correlated task evidence, and applicable readback/acceptance checks.
- Never silently retry non-idempotent card operations (create/write/format/key change). Maintain the explicit confirmation and verified state transitions required by existing flows.
- No hardware/card access, writes, formatting, recovery, or use of customer media without explicit approval for that specific test. Recovery/FormatPICC requires distinct destructive approval. Software CI and synthetic fixtures are **not** hardware acceptance.
- Keep productive keys, vault contents, customer/base profiles, raw card/payload bytes, credentials, certificates, local reader evidence, binaries, installers, and build caches out of the repository and out of logs, reports, test fixtures, and PR text. Only synthetic, non-sensitive fixtures may be committed.
- Preserve profile version/fingerprint binding, atomic save + optimistic revision checks, persistent sidecar locks and exclusive workspace lease, project-local path containment, and key-free evidence.
- Respect supported DESFire file types and evidence limitations; never add UI-only support that the engine cannot safely execute and verify.

## Build, test, and release

- Development baseline: Windows, PowerShell, .NET SDK from `global.json`.
- **Batched development and test milestones (21.11.2026):** Implement several cohesive UX/Vault/project/station improvements first, secure the incremental source commits, and add focused synthetic regression cases as code. Do **not** demand a new MSI, Windows session, UI click-through, workflow execution, or release after every small edit/commit. Treat the first release as a **single milestone acceptance**, not a stream of mini-releases. Exceptional critical blockers must be identified transparently, not masked.
- **Single GUI / headless central server is mandatory:** SieEncode Studio is the **sole** application for creating, editing, approving and managing customers, all keys/versions, projects, users/devices/groups, policies and recovery. The central component is a **headless** authenticated storage/sync/authorization/revision/audit service with **no separate web admin UI or data-entry UI**. It accepts/rejects versioned change commands from SieEncode and returns conflicts to resolve **inside SieEncode**. Offline edits are distinguishable from centrally accepted revisions. No additional workflows/buttons to make users administer the server outside the Studio.
- **First-release baseline clarified:** SieEncode is developing its **first 1.0 release**. There are no previously released SieEncode project files or Vault files needing customer migration. Internal candidate numbers are **not** prior production releases. **Do not build backward-compatibility, old-project/Vault migrations, shadow storage or special test matrices solely for nonexistent released versions.** We may consolidate and change internal candidate file layouts before 1.0 when useful; **reuse functional code** instead of discarding working AES-GCM, groups/recovery, project editor, station or RFiDGear wiring. Existing candidate fixtures are internal and may be adjusted in focused test updates. This release status **does not waive security validation, correctness, backups, recovery testing or card-write approval**. The intended workflow is one SieEncode client/UI managing a central, full offline-capable key library with suitable group/recovery controls; do not conflate certificate possession and key authorization.
- **Central sync code is NOT a deployed central server:** `KeyLibrarySyncTransport` signs and verifies the exact encrypted Vault byte hash (not the local pre-encryption payload), `CentralKeyLibraryStore` registers independently pinned authority and atomically rejects central CAS/replay conflicts and non-increasing **signed/catalog-claimed** logical revisions, `KeyLibraryDownloadAuthorization` requires an enabled member-device signature and short expiry for encrypted reads, and `KeyLibrarySyncClient` checks actual local decryptability, matches the claimed catalog revision to decrypted bytes, and verifies immutable key history before installing a newer encrypted revision. The existing administration signer produces central upload requests without exposing private authority keys. Synthetic end-to-end tests are registered, not yet compiled/run. These are Core library components, not a running TLS service or integrated automatic synchronization workflow. Central server cannot inspect the plaintext history; client validation and trusted administrator authorization are part of the model. Production HTTP authentication, anti-replay beyond short-lived read requests, central policy rotation and recipient rewrap, audit, server-signed acknowledgement, durable anti-rollback anchors and user/role-specific encrypted access remain incomplete. Never claim the headless central service or live sync is production-ready.
- **Offline revocation is NOT retroactive:** A former member who retained an older ciphertext Vault, the old signed policy and the former matching private certificate may decrypt historical secrets regardless of the current signed revocation. Importing the new policy does not erase another offline copy. Never label mere group removal, policy export or current Vault rewrapping as a complete revocation of DESFire card keys. Re-Key of affected cards and readers/SAMs is separate, requires hardware verification and is never triggered implicitly by UI. Do NOT create previous-epoch Vault backups in a shared project folder; default history must stay in the operator's local user profile, and file ACL/privacy controls must be checked independently. See `docs/design/OFFLINE-ENTZUG-GRENZEN-1.0.md` for the security decision gate; hard immediate revocation requires a different key-service/hardware design.
- **Key management requirements clarified (21.11.2026):** SieEncode must serve as a **general, central DESFire key-management system** as well as a project builder/coding tool. Authorized operators **must be able to view, copy and export plaintext keys when necessary**, including for SIPORT configuration; secret values are not limited to coding operations. A constant Internet/server connection and SAM-equipped readers are **not viable prerequisites**. The endorsed design is one centrally governed, versioned per-customer key catalog with an **always-carried complete encrypted offline copy of the authorized library**. The fully authorized administrator carries **all customer keys and historical versions** by default, without preselecting customers or generating per-trip packages. Other users receive their centrally authorized decryption scope; merely hiding values in the UI is not a security boundary. Offline catalog synchronization is automatic when connectivity is available or uses signed/encrypted removable-media transfer, with dedicated key-view/export permissions, auditing and verified key rotation workflows. The compromise of one fully authorized offline client can impact the entire customer key estate, and this risk must be explicitly documented. Do not reintroduce mandatory HSM, SAM, online-only crypto providers or a non-exportable-only Vault as 1.0 prerequisites. Prior design instructions asserting online KMS and never readable keys are superseded by `docs/design/ZENTRALE-SCHLUESSELARCHITEKTUR-1.0.md`. Continue to avoid accidental disclosure: no raw keys in git, ordinary logs, test fixtures or automatic reports. Availability to explicitly authorized humans is **not** permission for unguarded key display.
- **Central key catalog MUST evolve from existing code, not a rewrite:** The complete encrypted, offline usable key catalog is the future source of truth. Stable `KeyId + Version` references should lead through a checked resolver into the existing `ProjectKeyVaultPayload` / `ProjectKeyVault.Apply` and established RFiDGear build/session path. Preserve current project editor, profile tools, `GroupVaultService` primitives, group trust, recovery, project catalog and station; avoid two independently editable permanent secret stores. The group Vault now has a separate authenticated library purpose/domain; preserve the project-vs-library protection boundary. Current implementation stages: `KeyLibraryContracts.cs` (key-free metadata), `KeyLibraryVault.cs` (encrypted full offline snapshot reusing group AES-GCM/certificates/recovery and immutable value generations), `ProjectKeyLibraryResolution.cs` (key-free per-project customer/library/slot -> `KeyId+Version` binding, strict complete typed PICC/transport/AID slot resolution into existing transient `ProjectKeyVaultPayload`), `ProjectJson` catalog-bound safe-load/save guards (raw secrets in such files always rejected), and `KeyLibraryEditing.cs` (in-app import/generation/new version/status business operations, no automatic card rotation). Synthetic regression cases are registered in the existing test harness, **not executed yet**. The new library Vault currently grants its selected group access to the whole document and has a 16-MiB outer format limit; per-customer cryptographic permissions, recipient rewrap, secure production backup, **initial Studio project-key assignment** exists behind the editor's existing key action. The signed-administration dialog now also contains an initial local customer/key editor (with administrator signing-key and exact trust-checkpoint checks, plus separate member-Vault decryption), backed by stable customer IDs and an encrypted full library. **This is code only and untested:** non-admin customer-level view/export policy, a centrally signed atomic mutation contract, authoritative headless synchronization, audit, production backup/recovery and actual Runtime use remain unimplemented. The KeyLibraryVaultStore.Create/Update persistence methods now require a verified `SignedKeyLibraryMutation` from the current RSA signing authority and pinned local group-trust checkpoint, tied to previous vault file hash, catalog revision, library/group and a SHA-256 of the exact next logical payload. Studio signs it inside the established administration workflow, and synthetic denial tests are registered but NOT yet built/executed. This closes the previously unsigned regular *local file-write* path but is NOT the central authority/sync protocol; the headless server still needs an authenticated signature over the actual encrypted transfer envelope, server monotonic revisions/conflict protection, audit and verified offline-rollback handling. The existing payload hash is computed from normalized JSON *before encryption*, not a ciphertext digest, so do not pretend it is already independently verifiable by a blind server. No production acceptance or non-admin key-view/export role policy exists yet. No new UI button should be introduced unless required for the single intuitive Studio workflow. **Do not present it as a working central key-management system or store customer secrets in it yet.** Continue in phases in `docs/design/SCHLUESSELBIBLIOTHEK-INTEGRATION-1.0.md`. Catalog-bound projects deliberately disable legacy project-Vault actions and the build path until authenticated version-pinned session resolution is integrated. The key-selection dialog needs a previously provisioned encrypted local catalog; it is not yet a management UI. Never enable a catalog binding until exact-version resolution is secured and fail-closed; do not ask operator to preselect field customer keys.
- **Key diversification is explicitly OUT OF SCOPE for SieEncode 1.0:** Do not implement, plan, suggest, design, test, expose or require DESFire key diversification, diversification profiles or derivation parameters as part of this release. Manage the actual explicitly entered/authorized customer keys and versions without changing how each customer's host/readers use them. Do not delete pre-existing internal code solely for this scope change; do not build additional diversification infrastructure. See `docs/design/ZENTRALE-SCHLUESSELARCHITEKTUR-1.0.md`.
- **No impossible revocation claim:** Since authorized staff can access raw DESFire keys offline, central removal can stop *future authorized sync/issuance* but cannot retract secrets already viewed, exported or decrypted from old snapshots. A cryptographically meaningful response to compromise requires controlled rotation on affected cards and readers, including SIPORT configuration where applicable. Offline audit trails are best-effort until verified upload; do not advertise them as tamperproof against privileged local users.

Reuse valid unchanged evidence; focus manual checks on new or impacted workflows. No release without the appropriate Windows, installer, security and hardware acceptance evidence.

## Official RFiDGear bridge migration (2026-11-20)

- Keep the shipped Runtime and its historical evidence intact. Work incrementally behind an **optional** adapter and require a separate parity and hardware acceptance before switching it on. Never equate the new upstream v2.1.0 installer with the unpublished v2.1.1 master features.
- Upstream issues: `c3rebro/RFiDGear#232` (bridge), `#233` (auto mode), `#234` (key providers). Current host capabilities `project.revision` (PR #396) and `Check UID` with runtime variable (PR #397) exist on upstream `master` as of 2026-11-20, **not** in published v2.1.0. Gate by actual `hello.capabilities`, not a version number.
- On the bridge use `hello.instanceId` + opaque `projectRevision`, pass `expectProjectRevision` to `startRun`, and preserve a distinct persistent Studio-approved project/profile/payload digest. External files and persisted payloads are not covered by the upstream in-process revision.
- A writing job must be tied to a fresh card approval. Until upstream provides one-shot AutoMode approval, restrict writes to single `startRun` operations: `scanReader` → Studio approval → `Check UID($EXPECTEDUID)` as a gating task → all writing tasks conditional on that check → independent read-only acceptance after a remove/reapply cycle. A UID match is *not* cryptographic card authentication. Do not use an AutoMode startup variable as a reusable writing authorization.
- Persist a unique request ID **before** sending `startRun`. If start outcome is uncertain, query `getRunResult` with the same ID; never retry a non-idempotent write with a new ID. Mark unknown/bridgeFault/lost task detail as requiring independent inspection. Treat bridge project revision as valid for one host process only; reapprove after host restart.
- Upstream PR #398 (`keys.context`) has merged into `master`: `resolveKey` now includes optional requestId, source and projectRevision; `registerKeyProvider(ownRunsOnly=true)` lets the host refuse non-client runs itself. Require capability `keys.context`, verify the response confirms `ownRunsOnly`, and additionally bind every vault decision to the approved request ID, instance, project revision, UID, AID, key slot, usage and reference. **Not included in the published v2.1.0 release.** No productive vault resolution until our adapter has negative tests and independent hardware acceptance.
- Upstream PR #399 (`execution.verificationDetails`) has also merged into `master`: only DESFire `Check File Settings` currently provides versioned non-secret numeric comparisons through `TaskOutcomeDto.verificationDetails`. Accept unknown kinds/versions safely; a terminal success or matching UID is **not** independent card readback. Neither #398 nor #399 is in published v2.1.0.
- PR #400 proposes an approved single-run sample; PR #401 proposes including project revision on AutoMode results. **Both are open, not released** as of 2026-11-20. AutoMode has no one-time after-presentation approval yet: no productive writes by AutoMode.
- The canonical additional test design and remaining gaps are in `docs/design/RFIDGEAR-BRIDGE-ABNAHMEVORSCHLAG.md`. Read it together with upstream `RFiDGear.Bridge.Contracts/CLIENT-GUIDE.md`; tests using simulated readers do not count as real reader/card acceptance.
